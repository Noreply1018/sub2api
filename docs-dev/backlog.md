# 二开需求池

本文记录本 fork 的二次开发需求。每个需求保持简短，只写清楚目标、范围、验收和状态；复杂设计另开专题文档。

## 使用规则

- 先记录需求，再选择一个最小可交付项开发。
- 小改动可以只写一句目标；涉及网关、计费、权限、支付、数据库的改动必须补齐范围和验收。
- 新需求记录 `记录` 日期；完成开发和自测后补 `验证` 日期、环境和关键结果。
- 完成开发和自测后，先保持 `doing` 或标记为待验收；必须经过用户验收确认后，才能把新功能状态写成 `done`。
- 提交信息中体现需求主题；状态更新为 `done` 的提交应发生在用户验收确认之后。
- 涉及前端语义隐藏的改动不能只看源码 diff、单测或 build；必须在 8081 开发环境做真实浏览器页面检查，截图并结合可见文本断言。
- 不把临时想法扩写成大段 PRD，避免 backlog 变成难维护的说明书。

## 状态说明

- `idea`：只是想法，尚未确认。
- `planned`：已确认准备做。
- `doing`：正在开发。
- `review`：开发和自测已完成，等待用户验收确认。
- `done`：已完成、已提交，并且已经用户验收确认。
- `paused`：暂缓。

## 前端语义隐藏验收

对 personal/simple 模式、权限控制、入口隐藏、计费/充值/余额文案移除等 UI 语义类任务，验收必须覆盖：

- 在 8081 开发环境确认目标运行模式和关键配置已生效，不能只看组件条件渲染。
- 用真实浏览器访问相关页面并保存截图。
- 从页面可见文本提取结果做断言：应出现的核心信息必须存在，应隐藏的入口、卡片、按钮、金额符号和中英文文案必须不存在。
- 8080 日常使用版不能参与开发验证；除非用户明确要求发布，否则不得重建、重启或改动 8080。

- 目标：一句话说明要解决什么问题。
- 范围：涉及后端、前端、部署、文档中的哪些部分。

### D003: 个人模式移除余额扣费语义

- 状态：done
- 目标：让本 fork 的个人/小规模网关不再依赖用户余额，调用只依赖鉴权、分组、账号调度和用量记录。

- 验收：余额为 0 的用户仍可使用有效 API Key 调用；请求完成后 `users.balance` 不变；`usage_logs` 继续记录 token；前端不再暴露余额、充值、账号倍率和分组倍率入口。
